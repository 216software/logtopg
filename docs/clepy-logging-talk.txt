++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++

How to use logging
==================

Assuming you have logging configured somewhere else, this is all you
gotta do.  ..code:: python

    import logging

And then either this (most of the time).  ..code:: python

   log = logging.getLogger(__name__)

That __name__ will be something like "yourpackage.yourmodule" or
"yourpackage.parentmodule.yourmodule".

Or do this instead if you're in a script, because in a script, __name__
will be "__main__".  .. code:: python

    log = logging.getLogger("bogusproject.cronjobs.do_daily_chores")

And then after setting up that module-level variable, you just do this.
.. code:: python

    log.debug(f"Got {len(chores)} chores to do today")

Exceptions need a little bit of different handling. .. code:: python

    try:
      do_something_risky()
    except Exception as ex:
      log.exception("It didn't work!")

Logs have these levels: .. code:: python

    log.debug("Got this far and x is %s", x)
    log.info("User %s just logged in", user)
    log.warn("User %s is trying to access something they shouldn't!", user)
    log.error("3rd party API unavailable; queueing data instead")
    log.critical("I can't recover from this!  Wake somebody up.")

By the way, log.exception is the same as doing: .. code:: python

   log.error(..., exc_info=True)

I have *opinions* about how and when to use the different levels:

* debug is for... debugging. don't spam your logs!

* info tracks state-changing operations, like login, logout, charge a
  credit card, etc.

* warning is for stuff like "this method is deprecated; use fibityfoo()
  instead"

* errors are for caught exceptions

* critical is for uncaught exceptions

What happens inside log.debug(...) or whatever
==============================================

The "log" object is a logger.  Each logger has a parent logger and a
list of handlers.  The log message gets sent to each handler, and if the
log object has "propagate" == True, then the log message also goes up to
the parent log object.

Performance Costs of Logging
============================

Theoretically, logging slows down your code in two ways:

1.  Every log.debug(...) method call (or log.critical(...)) requires
    checking the configuration to decide whether to emit this log
    message.

    If you add a million log.debug(...) calls in an API handler, you're
    making the code check what to do with log.debug messages a million
    times.

2.  String interpolation is not free, so this is what you're supposed to
    do: .. code:: python

        log.debug("Got this far and x is %s", x)

    Rather than: .. code:: python

        log.debug(f"Got this far and x is {x}".)

In practice, I don't worry about it!

Tangent: python vs common lisp
==============================

If python were as cool as (and as confusing as) common lisp, then there
would be a way to say for this line: .. code:: python

    log.debug(f"Got {len(chores)} chores to do today")

"Don't even evaluate the stuff inside debug(...) unless I tell you!"

But we don't have that kind of power in python (and for good reason --
common lisp drives you mad).

If you want to learn more, read "Practical Common Lisp" by Peter Siebel
(free book online) here: https://gigamonkeys.com/book/

It's a great book!

How to configure logging
========================

You have three ways to do it (3rd is my fave):

1.  Do method calls to build the loggers, handlers, formatters,
    and filters

    See example_code_based_config.py for an example.  It has lines like
    this: ..code:: python

        h2 = logging.StreamHandler()
        h2.setLevel(logging.DEBUG)
        h2.setFormatter(fmt)
        logging.root.addHandler(h2)

2.  Load in a configparser-style cfg file. See fileconfig_example.py for
    an example.  It looks like this: .. code:: python

        import logging
        import logging.config

        if __name__ == '__main__':

            logging.config.fileConfig("simple_example.cfg")

            logging.debug('This is a boring debug message.')
            logging.info('Here is an info message...')

3.  Load in a dictionary from whatever config you want: .. code:: python

        import logging
        import logging.config

        d = yaml.safe_load(yaml_style_config)
        logging.config.dictConfig(d)

Tangent: yaml anchors, aliases, and overrides
=============================================

Here's a yaml file with some redundant info.

.. code:: yaml

    # costumes-1.yaml

    # This is Matt's costume
    matt:
      shoes: red
      pants: red
      belt: red
      shirt: red

    # Oswald wears costume same as Matt
    oswald:
      shoes: red
      pants: red
      belt: red
      shirt: red

    # Rudy does the same except different belt
    rudy:
      shoes: red
      pants: red
      belt: white
      shirt: red

With anchors and overrides, we can define the same thing with less
work.

.. code:: yaml

    # costumes-2.yaml

    matt: &mattcostume
      shoes: red
      pants: red
      belt: red
      shirt: red

    # oswald wears same as matt
    oswald: *mattcostume

    # rudy is same but wears a white belt
    rudy:
      <<: *mattcostume
      belt: white

This means if we decide we are all switching to green shoes, we only
need to update one place!

Now, how to use logtopg
=======================

Install it with: .. code:: bash

  $ pip install logtopg

Create a postgresql database and user for your logs::

    $ sudo -u postgres createdb --owner matt clepy_logtopg_demo

Add the "ltree" extension (it's built-in, but not enabled):

    $ sudo -u postgres psql -d clepy_logtopg_demo -c "create extension ltree;"

Add code in your project to add logtopg to your handlers (use the
yaml_example.py file if you want).

Other details
=============

You probably want to delete old logs in a daily cron job (or something
like that)::

  psql -c "delete from clepy_logtopg_demo_logs where inserted < current_timestamp - interval '7 days';"

History / Why / Inspiration
===========================

One company I worked at had a customer web application stack that would
catch any uncaught exception, convert it to a string, and then store
that string (and some of the details about the environment) into a
database table.  A custom web app polled the database and displayed
tables and charts of errors.

This was sort of like a proto-sentry.  It worked great.

----

Later we worked on a different project where a linux box in a machine
shop read data from dozens of sensors and recorded data every second at
least.

We added a screen to the webapp that did something like this:

  $ tail -f app_log.txt | grep SENSOR | grep INFO

And clients LOVED seeing the near-real-time logging data.  They trusted
the system way more when they could watch the sensor data flow by.
